# Project VM host verification

The initial probe passed on Apple Silicon with macOS 26.5.1, OrbStack Docker Engine 29.8.2, Docker Compose 5.5.0, and Lima 2.3.0 using VZ in plain mode. The probe used a temporary Lima directory and a guest with two CPUs, 2 GiB of memory, and a 10 GiB disk.

The guest was Ubuntu 24.04 ARM64. The Lima template verified the image digest `sha256:50e24e1fb79e89116e939d90aa7738f7af48c442fa1bc2510131e0b39c50348e`. [Lima release](https://github.com/lima-vm/lima/releases/tag/v2.3.0) · [Ubuntu image](https://cloud-images.ubuntu.com/releases/noble/release-20261017/ubuntu-24.04-server-cloudimg-arm64.img)

Lima's Unix socket path has a platform length limit. If initialization reports that the provider path is too long, use a short host directory for `LIMA_HOME` and restart the provider. Choose this location before creating projects: existing VM disks and their bindings remain under the original Lima home if it is changed.

A marker written to the guest disk survived stopping and starting the same named VM. The running OpenBot server container reached a temporary loopback adapter via `host.docker.internal`. The adapter read the marker over Lima's guest shell, confirming the container-to-host-to-guest path. The Linux host profile and the production adapter’s project binding and network controls remain to be verified during implementation.

The disposable macOS guest probe found that Lima's default guest user has passwordless administrator access. Project commands instead run as a separate unprivileged account in a private Linux network namespace. The namespace has only loopback and no outbound routes; IPv4 and IPv6 access to the host, other guests, and external networks is denied by default. The provider checks the namespace, routes, account capabilities and sudo access before marking it isolated or running a command. Project readiness and actions remain blocked if the checks fail. The Apple Silicon VM test has verified this behavior; the Linux host profile and configurable approved egress still need validation and implementation.

Guest actions use stable operation keys and keep a completion receipt in the guest as well as a host-side record. Before reporting an action or source import complete, the guest flushes its disk. If the connection drops after an action finishes, reconciliation can recover its exit code and output from the guest without executing it again. If no completion receipt is available, the outcome remains uncertain and the provider does not automatically repeat the action. On the host described above, disposable VM tests recovered a result after a simulated lost response, verified one guest write, and retained the result and workspace through both a normal restart and a forced stop. A forced stop initially lost an unflushed write; the successful retest used the new flush. This verifies those test cases, not every possible host or storage failure. The complete network-isolation and workflow acceptance scenarios are still pending.

When a project source folder changes, the provider retains the previous guest workspace under `~/.openbot/backups/` before importing the new baseline. It checks the prior source revision and keeps an interrupted import retryable. A disposable guest test verified that an edit made in the first workspace remained in that backup after the replacement. Source folders on the host are read only during both imports.

After building the pinned OpenBot server image, run `sh test/integration/project-initialization.sh` from the repository root to repeat the isolated PostgreSQL checks for project identity, import retries, source replacement, and readiness invalidation. The script removes its temporary container and network when it exits.

With Lima installed on a supported host, `npm run build && node test/integration/workspace-vm.mjs` repeats the disposable VM recovery and source-replacement checks. Set `LIMACTL_PATH` if `limactl` is not on the path. Set `OPENBOT_TEST_FORCE_STOP=1` to test a forced stop instead of the normal shutdown. This test creates and removes its own temporary VM and Lima directory; it does not operate on project VMs.
