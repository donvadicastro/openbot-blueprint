# Business workflow engine

This is the in-progress Temporal execution path selected in the business-platform plan. It pins Temporal Server `1.29.7` and TypeScript SDK `1.25.0`, and uses a private PostgreSQL database. The overlay has no published database, Temporal, or worker ports. Its PostgreSQL volume is separate from the OpenBot database. The worker image tag defaults to `COMPOSE_PROJECT_NAME`; the provisioner sets it to the installation name so building one provisioned installation does not overwrite another's default tag. When running Compose manually, set it to the same value as `--project-name`. `WORKFLOW_WORKER_IMAGE` overrides this for controlled deployments or tests.

The worker preserves decision waits in Temporal history. Phase activities use one attempt: an unconfirmed result pauses the run until an authorized caller requests reconciliation, which must establish whether the effect occurred before another attempt. The private gateway binds each workflow ID to its installation, project, run, and pinned plan. The product module writes the initial dispatch intent in the same database transaction as the plan.

A confirmed specialist failure can start a new occurrence according to its blueprint retry limit and delay only when the earlier turn saved no output and reserved no workspace action. The new occurrence keeps the same pinned inputs and records its retry lineage. Temporal persists the delay; a reserved or uncertain action remains held for reconciliation instead of being automatically repeated.

The root `docker-compose.yml` and the blueprint provision command start the same private Temporal services; `compose.yml` remains as a compatibility fragment for existing test and operator commands that already list it. This is not yet a complete operational workflow. OpenBot starts its outbox scheduler and authenticated activity endpoint when connected to the workflow worker. Built-in specialists can run with project-scoped output tools and, where permitted, a workspace action with durable evidence. Decisions bound to a validated phase result are stored and delivered through a retryable outbox; fixture tests cover answering during worker downtime. The QA dispatcher uses a candidate-bound protected checkout and records scenario progress. Fixture tests cover rework after a failed scenario and an authorized retry when a scenario is blocked; actual-model execution remains unverified. Internal relative symbolic links are supported; links that escape the checkout and candidates with archive exclusions are rejected. Tests must write to temporary storage and have no outbound network access. Remote AG-UI declarations can use the native scoped headless runner; a disposable AG-UI HTTP fixture verifies the native scoped tool exchange, while full remote workflow and model acceptance remain unverified. General MCP tools and approval-required actions other than the SWE staging path are not yet connected; those phases remain uncertain and require reconciliation. An actual-model end-to-end pilot and the remaining acceptance scenarios have not been completed.

The Team Lead can call `project_work` to inspect runs in its authenticated conversation and follow authorized output references through `project_artifact_read`. The SWE blueprint grants it access to deployment evidence; the run-linked output is omitted if the approval evidence is restricted. Model-generated summaries remain unverified.

The originating project conversation has a project-work panel with authorized workflow decisions and selectable blueprint-defined specialist views. Its state stream sends an AG-UI snapshot when opened and replacement deltas when durable progress changes; reconnect starts with a fresh snapshot. OpenBot's uncached session guard and access to the conversation and referenced artifacts are rechecked during the stream. A revoked session or conversation clears the displayed state, and a restricted candidate, test plan, brief or report removes its QA scenario details. A disposable Chrome fixture checks QA progress, structured fields, release evidence, approval and the final verified outcome. Full-stack browser acceptance is still pending.

Validated temporary SWE workflows may use the supported staging release phases when every route into deployment comes from the release preparation phase; the same evidence and human approval checks apply. Other approval-protected temporary actions remain unavailable.

The SWE project setup also accepts an optional release runbook and release target. Preparation rechecks those inputs, the source baseline, the candidate and the passing QA evidence, then asks an authorized person to approve or reject that exact candidate and target. A deployment runs only when the approved target matches the configured staging adapter. Its operation key is committed first; an uncertain response is looked up before any repeat, and a separate verification must succeed before the workflow reports a verified release. The adapter must deduplicate concurrent calls by operation ID and must verify the exact candidate and target independently. The configured endpoint origin is bound to the operation, so an uncertain effect cannot be reconciled against a different service. The original requester sees when an action is awaiting reconciliation and can use “Check and recover interrupted work” in the project conversation. The status endpoint rechecks project and conversation access and returns only the engine state.

For a disposable pilot, set `STAGING_TARGET_TOKEN` to a random value of at least 32 characters and `STAGING_TARGET_ID` to the same value supplied in the project’s release target, then add `-f deploy/workflow/staging-fixture.compose.yml` after the base and workflow Compose files. This fixture records a durable, idempotent test effect; **it does not deploy application code**. Set `STAGING_DROP_FIRST_RECEIPT=true` to exercise recovery from a lost response. For another adapter, configure `STAGING_TARGET_URL`, `STAGING_TARGET_TOKEN`, and `STAGING_TARGET_ID` in the native environment; the adapter must implement the private deploy, lookup, and verify protocol. Leave them unset to keep deployment disabled.

The adapter receives authenticated JSON `POST` requests with a bearer token. Deploy and lookup receive `{operationId, projectId, candidateDigest, target}`; successful deployment or lookup returns `{status: "confirmed", receipt: {...binding, receiptId}}`. Lookup may instead return `{status: "not-found", ...binding}` only when absence is authoritative. Verification receives the receipt and returns `{status: "verified", verification: {...receipt, verificationId}}`. The adapter must bind every response to the exact request, retain operation IDs across restarts, and make repeated or concurrent deploy calls for the same binding produce one effect. An error or malformed response is treated as uncertain.

From the repository root, `bash test/integration/chat-ui.sh` builds a disposable pinned app and checks the chat panel in headless Chrome with fixture data. Set `CHROME_BIN` if Chrome is installed somewhere other than the default macOS location. The test does not connect to an existing OpenBot installation.

`bash test/integration/staging-fixture-container.sh` tests the disposable staging fixture's lost-response recovery, verification, and persistence across container replacement.

In the OpenBot Projects page, select a project and open a work item under
**Project work** to see its phases and answer a pending question or decision. Available
choice options come from the pinned workflow and the validated result. A saved answer
is queued durably if the worker is unavailable; the status remains visible while
delivery is pending. The project API exposes the same scoped work list and
decision endpoint to authenticated project and conversation members.

The overlay requires `WORKFLOW_POSTGRES_PASSWORD`, `WORKFLOW_ACTIVITY_TOKEN`, and `WORKFLOW_ENGINE_TOKEN`; use distinct random values and store them in the native environment file. The activity and gateway tokens must each contain at least 32 characters. It can be inspected without starting services:

```sh
docker compose -f docker-compose.yml -f deploy/workflow/compose.yml config --quiet
```

From this directory, `npm ci && npm test` runs an isolated Temporal test server. The recovery test stops the worker while a decision and an uncertain effect are pending, sends messages while it is down, and verifies that the replacement worker resumes without repeating the effect. These tests use a fixture activity, not a real OpenBot bot or staging target.

From the repository root, `sh test/integration/temporal-compose.sh` exercises a disposable Compose installation with real Temporal and PostgreSQL containers. It restarts Temporal and the worker, then checks that a waiting decision resumes and an effect committed before a lost response is reconciled exactly once. The script removes only the uniquely named containers and volumes it creates.

`bash test/integration/workflow-adapter-compose.sh` also snapshots the disposable product and Temporal databases during a decision wait. It restores them under separate database names, removes transient membership records only in the restored copy, and starts an isolated Temporal server, worker, and product adapter. The restored run completes with one simulated workspace effect while the original remains waiting. This is a fixture recovery test; it does not restore a real VM or prove a coordinated production backup procedure.
