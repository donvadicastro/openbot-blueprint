# Research: Business Operations Platform

## OpenBot integration and deployment

**Decision** — Keep the OpenBot revision recorded in [upstream.json](../../deploy/openbot/upstream.json) as the pilot baseline. Extend the existing Projects UI and folder picker, use native authentication, chats, governed tool calls, and tenant export, and add one TypeScript product module at the authenticated server boundary. Keep its DB migrations and runtime adapter in the existing OpenBot overlay. Identify Compose deployments by blueprint key across versions and assign distinct names, host ports, data, credentials, and provider namespaces to distinct blueprints. Use the existing Compose init service to validate and export the tenant. A host-side provision command owns the installation binding and serializes creation for the same key.

**Rationale** — The [current Compose guide](../../docs/docker-compose.md) and [overlay installer](../../deploy/openbot/team-intake/install.ts) show which surfaces already exist. The stock setup flow is conversation oriented and does not represent all project readiness checks, access grants, or workflow records. The pinned commit is [published upstream](https://github.com/CopilotKit/OpenBot/commit/ab9855c19848378c90a806426130d86699cc798c). The adjacent local OpenBot checkout is at a different revision and cannot prove behavior at the pin. Verify the overlay and native entry points in a pinned build before extending them.

**Alternatives considered** — A separate app would duplicate identity, chats, and tool governance. A separate installation for each project would break project creation inside the running blueprint app. A broad OpenBot fork would increase upgrade work. [OpenBot architecture](https://github.com/CopilotKit/openbot/blob/main/docs/architecture.md) · [Compose project naming](https://docs.docker.com/compose/how-tos/project-name/)

## Workflow execution and operator history

**Decision** — Use one engine interface for published and temporary workflows. Validate native OpenBot scheduling and handoffs against SC-014 first. Plan the fallback as a private self-hosted Temporal service and TypeScript worker in Compose. Keep non-deterministic operations in activities behind OpenBot policy and the tool gateway. Start via an outbox and a stable run identity. Use action operation keys and target reconciliation for external effects. Project members see a project-scoped history in OpenBot. Treat engine history as operational metadata and keep credentials and raw artifacts in their existing stores.

**Rationale** — The current stack documents a native routines worker and handoffs. The pinned queue provides leases, deduplication and attempt limits. The pinned worker dispatches routines and purges old entries. Durable business phases, persistent waits, and operator history still need a native integration proof. [Pinned queue](https://github.com/CopilotKit/OpenBot/blob/ab9855c19848378c90a806426130d86699cc798c/server/src/work/queue.ts) · [Pinned worker](https://github.com/CopilotKit/OpenBot/blob/ab9855c19848378c90a806426130d86699cc798c/worker/src/index.ts) Temporal provides event history, replay, and workflow messages. Side effects still need idempotency and reconciliation. Test both workflow kinds with a worker interruption during a wait and another after the target commits an effect but before the worker records its result. [Native routines](https://github.com/CopilotKit/openbot/blob/main/docs/routines.md) · [Temporal event history](https://docs.temporal.io/workflow-execution/event) · [Temporal activities](https://docs.temporal.io/activity-definition)

**Alternatives considered** — LangGraph persistence and interrupts are useful for agent-level flows. Using it as the business engine would also require proving the operator history and effect handling at the project boundary. n8n has inspectable executions and retries. A retry can repeat partially completed work within a failed node, and bundling is subject to its Sustainable Use License and DC-003. Prefer a single execution engine for the pilot. [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) · [n8n execution history](https://docs.n8n.io/build/understand-workflows/understand-executions/view-all-executions.md) · [n8n license](https://github.com/n8n-io/n8n/blob/master/LICENSE.md)

## VM and source intake

**Decision** — Use host-managed Lima guests, with VZ on macOS and QEMU on Linux, behind a narrow authenticated workspace adapter. Provision under a stable installation and project key. Use a pinned Linux guest image and persistent disk, disable host mounts and dynamic port forwarding, and authorize access to the assigned guest through the project module. The host adapter authenticates OpenBot, checks the project-to-VM binding, and offers only the workspace operations in the [contract](contracts/workspace-provider.md). Enforce isolation through guest networking and host access policy as well as the VM boundary.

**Rationale** — The existing supervisor provisions Docker containers. The spec requires a separate persistent VM per project, with disks independent of app restarts. Running the provider on the host avoids assuming nested virtualization inside Docker. Revalidate real-path containment when importing. Import a committed Git baseline with a verified bundle or copy an approved plain folder as a bounded snapshot and create its baseline in the guest. Report when a Git import excludes uncommitted files. Avoid following links outside the approved root or importing host Git configuration or credentials. Verify two guests from one source, duplicate creation, and recovery with guest edits intact. [Lima VM types](https://lima-vm.io/docs/config/vmtype/) · [Lima plain mode](https://lima-vm.io/docs/config/plain/) · [Git bundles](https://git-scm.com/docs/git-bundle)

**Alternatives considered** — Reuse the native supervisor for its existing computer tools. For the project VM itself, a Linux libvirt/QEMU/KVM host is a fallback if the supported deployment needs it. Keep that provider out of the pilot unless Lima fails the platform checks. [libvirt QEMU driver](https://libvirt.org/drvqemu.html)

## Chat state and role memory

**Decision** — Use AG-UI state snapshots and JSON Patch deltas with existing chat components where the pin supports them. Use the AG-UI 1.0 state contract and the pinned app’s @ag-ui/core 1.0.2. Reuse its A2UI 1.0 basic catalog where it fits. [Pinned app dependencies](https://github.com/CopilotKit/OpenBot/blob/ab9855c19848378c90a806426130d86699cc798c/app/package.json) · [Pinned renderer](https://github.com/CopilotKit/OpenBot/blob/ab9855c19848378c90a806426130d86699cc798c/app/src/lib/copilot/a2ui.ts) Project records are the authoritative source. Send an authorized snapshot at open or reconnect, and generate deltas from each viewer’s authorized projection. Use the same generic renderer for role-specific summaries and detail views.

**Rationale** — AG-UI already defines initial and incremental state events. A live QA card needs a persistent work/run reference that survives chat reloads and events that can arrive beyond the original agent response. Verify both on the pinned client before adding a small authorized stream adapter. Keep A2UI optional if the existing renderer already satisfies the role views. [AG-UI state](https://docs.ag-ui.com/concepts/state) · [AG-UI source and license](https://github.com/ag-ui-protocol/ag-ui) · [OpenBot releases](https://github.com/CopilotKit/openbot/releases)

**Decision** — Use native assignment memory only if it proves project and assignment scoping and correction history. The planned fallback is a PostgreSQL revision table in the existing product schema, fed by a narrowly scoped feedback action or skill. Inject only the current relevant guidance alongside configured skills and MCP tools. Persist the source and correction history in the product module. Workflow gates and tool grants remain enforced there.

**Alternatives considered** — Pinned Automatic Learning publishes skills from Intelligence learning containers scoped to bots and threads. Use it for that purpose. Assignment-level corrections and revision history belong to the project module. [Pinned Automatic Learning](https://github.com/CopilotKit/OpenBot/blob/ab9855c19848378c90a806426130d86699cc798c/docs/automatic-learning.md) A separate vector service is unnecessary for the pilot. Start with project and assignment lookup plus bounded retrieval of relevant entries.
